# Production environment and launch checklist

What Harbour (repository `freightX`) needs from outside the code to go live: every credential,
where it is set, what happens without it, and the business decisions that block launch whatever
the configuration says. The schema of every variable is in the root `.env.example`, with the
behaviour when unset; this page is the ordered checklist.

**Local development and tests need none of these.** The app runs on in-memory fallbacks, the
console email transport prints the magic link, and the test suite uses fixture tariffs and sample
FX. Every value below is set on the host (Vercel project settings today, the Fly.io or Railway
app later) and is never committed.

## 1. Two database connection strings, not one

Migrations and the running app use different roles (packages/db README, "Database roles"):

- `prisma migrate deploy` runs as the table owner (the `harbour` user of a managed instance),
  which needs `CREATEROLE` the first time so 0002 can create `harbour_app`.
- `DATABASE_URL` for the web app and the worker must be a **login role that is a member of
  `harbour_app`**, not a superuser and without `BYPASSRLS`; otherwise row-level security is
  silently off. Infra creates it by hand, once:
  `CREATE ROLE harbour_web LOGIN PASSWORD '…' IN ROLE harbour_app;`
- A separate worker role (`harbour_worker`) is planned but not built; the worker uses the same
  role for now.

## 2. The public calculator (Phase 0, live today on Vercel)

Runs with nothing set. Two variables matter before real traffic:

| Variable                                      | Why                                                                                         | Without it                                    |
| --------------------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------- |
| `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` | Cloudflare Turnstile on the calculator form (§7.5)                                          | Bot check off, one warning at startup         |
| `REDIS_URL`                                   | Shared rate limiter across serverless instances (the 20 calculations per hour per IP limit) | Per-instance limiter; the limit does not hold |

## 3. The workspace (Phase 1: sign-in, quotes, orders, bills)

These are the ones that close the workspace or make sign-in impossible in production:

| Variable                                                 | Where it comes from                                                                                                          | Without it in production                                                                                                            |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`                                           | Managed Postgres 16 in a UK region, as the `harbour_web` role above                                                          | Workspace says "needs a database"; the calculator keeps working                                                                     |
| `REDIS_URL`                                              | Managed Redis 7, same region                                                                                                 | Every workspace route answers 503 (sessions are never kept per instance)                                                            |
| `APP_URL`                                                | The public https origin, no path                                                                                             | Sign-in not available (magic links and the CSRF Origin check need it)                                                               |
| `EMAIL_TRANSPORT=resend`, `RESEND_API_KEY`, `EMAIL_FROM` | Resend account with the sending domain verified (decision (s) may pick another provider)                                     | Sign-in shows "not available yet"; the console transport is refused in production                                                   |
| `FIELD_ENCRYPTION_KEY`                                   | Generated by you, 32 random bytes base64: `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64'))"` | Workspace 503. The worker needs the **same** value. Losing it loses every encrypted EORI and VAT number: back it up like a database |

The worker (`apps/worker`) is a second process that needs `DATABASE_URL`, `REDIS_URL`,
`FIELD_ENCRYPTION_KEY` and, when those features are on, `CLAMD_HOST`/`CLAMD_PORT` and the
tracking provider keys. It is always-on (BullMQ), so it cannot run on Vercel. Until decision
(k) moves the whole app to Fly.io or Railway, the worker has no production host and the FX
refresh, tariff warm, quote expiry, identity checks, document scans and vessel polling do not
run.

Tuning, all optional, all with safe defaults: `LOG_LEVEL`, `FX_SEED_CSV` (a real HMRC monthly
CSV instead of the loud sample), `RATE_SHEET_PATH`, `BROKER_DEFERMENT_FEE_PCT` /
`BROKER_DEFERMENT_MIN_GBP` and `INLAND_VAT_ADJUSTMENT_{LCL,FCL,AIR}_GBP` (real terms only, see
decisions (l) and (m)), `STRIPE_EVENTS_CONSUMER` (leave at `web`), `ALERT_WEBHOOK_URL` and
`WORKER_PORT` for the worker. `SESSION_SECRET` is unused.

## 6. Deployment notes

- **Vercel (today):** root directory `apps/web`, Node 22, region `lhr1`; `apps/web/vercel.json`
  and the `vercel-build` script do the rest. Serverless means per-instance memory: set
  `REDIS_URL` before public traffic, and remember the worker cannot run here.
- **Target (decision (k)):** Fly.io or Railway, UK region, web app and worker in one deployment
  with managed Postgres 16 and Redis 7. Terminate TLS at the proxy and forward the right
  headers (decision (t)); rate limiting reads the client IP from `Fly-Client-IP`,
  `CF-Connecting-IP`, `X-Real-IP` or `X-Forwarded-For`.
- **Order of operations on a new environment:** create the database and the `harbour_web` role,
  run `pnpm --filter @harbour/db exec prisma migrate deploy` as the owner, set the section 3
  variables, deploy the web app, sign in with a magic link, create the first organisation, then
  switch on the section 4 features one at a time.
- **Sandbox note:** the Claude Code cloud container has no outbound route to the UK Trade Tariff
  API, so quotes made there come out INDICATIVE with `HS_UNVERIFIED`. That is the sandbox, not a
  bug; CI and the DB tests use the fixture tariff.
